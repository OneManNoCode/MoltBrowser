Touchless browsing: MoltBrowser by voice alone Status: proposal , October 2026.
Nothing here is built yet; §11 lists the owner's decisions that come before Phase 1.
The goal: a person who can't use a keyboard, mouse, touch screen or any other pointing device can use the whole browser with their voice.
They hear what matters read back to them.
If they have some sight, they see it large on screen.
Who it is for The person this is designed around: - They have lost the use of their arms and hands, so voice is their only input.
Close to the screen they can read large text, and otherwise they rely on hearing.
Output is therefore both: - Speech: what the browser heard, what it is doing, what it found, and the page itself when asked.
- A screen built for low vision: large captions, large numbered markers on everything that can be acted on, high contrast and magnification.
Some of these users have impaired or atypical speech , so recognition has to adapt to them, not the other way round (§9, Phase 4).
"YouTube is open." User: "Search for Bohemian Rhapsody." Browser: types into the site's search box and submits.
1: Bohemian Rhapsody, official video, Queen, 6 minutes.
2: Bohemian Rhapsody, live at Live Aid, Queen, 5 minutes.
Say a number or a name." On screen, each result carries a large number.
User: "Play the live one by Queen." (or "the fourth one") Browser: matches the words against the results' titles and channels and plays the video.
On those it reads the page through the accessibility tree (§6.3).
Core tasks each phase has to cover (§10): - Go somewhere: open a site, search, go back and forward, reload; open, close and switch tabs.
- Read: read the page, read headings and links, "what's on the screen?", summarize, find text, read the selection or the item under focus.
- Choose: by number, by name, by position ("the last one", "the next one"), with a readback when it's unclear.
- Act on a page: press buttons, follow links, fill forms by dictation, check boxes, choose options, scroll, zoom.
- Media: play, pause, volume, seek, speed, captions, full screen, next.
- Run the browser itself: settings, permission prompts, downloads, dialogs, the AI chat, MoltNet windows.
- Recover: "stop", "undo", "cancel", "what can I say?", "where am I?", "start over".
Voice in; speech and screen out.
No step ever needs a pointer or a key.
That includes the browser's own dialogs, permission prompts, error pages and first-run.
Every state can be left by voice.
"Stop", "cancel" and "go back" always work, and the browser never waits in silence.
If it can't do something, it says why and what the user can say instead.
Common commands are recognized by a small, fixed grammar without the language model, and start within about a second.
Only open-ended requests go to the on-device planner (§6.2).
The user decides, the browser confirms.
Before anything irreversible (buying, sending, posting, deleting, sharing data), the browser reads back what it will do and waits for a spoken "yes".
Wake phrase, recognition, voices and AI all run locally in sandboxed processes, like the rest of MoltBrowser's AI.
No audio is stored unless the user asks.
Audio a page plays, or text a page shows, is never taken as the user's instruction (§7).
Works with the OS's assistive technology.
MoltBrowser's own UI stays fully accessible to screen readers and to OS voice control (Windows Voice Access, macOS Voice Control), for users who already rely on them.
No wake phrase, no streaming, English only.
A process start per utterance is too slow for a conversation.
On-device language model (llama.cpp, sandboxed), constrained JSON decoding Turns open-ended requests into structured actions.
It acts through page scripts in an isolated world ( ), which don't count as a user gesture: a video won't start with sound, and full screen and some buttons refuse.
Real-click gates Trust changes, the agent's Allow and MoltNet settings need a physical click.
A voice user can't give one: these need a voice equivalent that is just as hard to forge (§7.3).
MoltShield Removes consent banners, overlays and ads, so pages are simpler to read aloud and to choose from.
Chromium 156 ( , ); with ; ; Blink's accessibility actions The speech recognition service is the right home for an open-source recognizer: today it runs Google's closed SODA engine, which MoltBrowser doesn't ship.
Text-to-speech can take a built-in engine of ours.
The accessibility tree exposes every page's structure.
An accessibility "click" counts as user activation ( calls ), as it does for OS assistive technology.
How it feels to use 5.1 Listening - States: off , waiting (listening only for the wake phrase), listening (a command is being spoken), thinking , speaking .
Each has a distinct sound (an "earcon") and a large on-screen indicator.
This makes "the fourth one" or "yes" natural.
- Always-listening mode , for users alone at home: every utterance is a command.
It is safer with speaker verification turned on (§7).
- Barge-in: the user can interrupt the browser's speech ("stop", "next", or a new command).
- End of speech: voice activity detection decides when the user has finished, adjusted for slower speakers.
5.2 What the user can say Five layers, tried in this order: 1.
Many phrasings are accepted ("open", "go to", "take me to").
Dictation into the focused field: "type ...", "new line", "delete the last word", "read it back", "submit".
Tasks in plain language, handled by the planner: "find a train from Paris to Lyon tomorrow morning", "reply to the last email from Ana saying I'll be late".
Each step is spoken, with confirmation before anything irreversible.
Questions about the page: "what does this page say about prices?", "summarize this article", "what's in this picture?" (the on-device vision model).
"What can I say?" lists what fits the current page.
The browser also groups the page's repeated items: search results, videos, products, emails, comments.
It reads them as one numbered list, each item with its title and the parts that tell them apart (channel, author, duration, price, date).
5.4 Speaking back - Verbosity levels: - brief : confirmations and counts; - normal : plus the top items of a list; - full : the page read like a screen reader.
- Rate and voice are adjustable by voice ("speak faster").
- Secrets are never read aloud: passwords, one-time codes and card numbers ("password field, filled from your vault").
- Private content (mail, messages) is read aloud only after asking whether others can hear, unless headphones are connected.
5.5 The screen, for low vision - A caption bar in large type: - what was heard ("Heard: play the live one by Queen"); - what is happening ("Playing: ..."); - the state.
- Large number markers , and a thick focus ring around the current item.
- Magnification that follows the item being read or acted on: "zoom in", "zoom out", "bigger text".
- High-contrast and dark themes , and Chromium's forced colours.
- Reading mode: the article alone, in large text, read aloud with the sentence highlighted.
5.6 When things go wrong - Unclear choices: the browser asks ("Did you mean the official video or the live one?"), with the candidates numbered.
- Misheard words: "no, I said ..." corrects the last request, and "undo" reverses the last action where the browser can.
- Failures: something that fails is said plainly, with a next step ("The site wants you to prove you're human.
I can switch to its audio challenge and play it; you say the answer.").
- Errors and crashes: the browser reopens what was open and says so.
In voice mode it never leaves the user in a silent state.
Architecture 6.1 Speech service - Process: a sandboxed utility process.
- Chromium's speech service: already captures the microphone inside the service ( ) and streams results over Mojo.
MoltBrowser would add an open-source recognizer next to the SODA one, which it never ships.
echo cancellation (WebRTC's, already in MoltBrowser), with the browser's own output as the reference; 3.
streaming recognition with partial results (shown live in the caption bar); 6.
final text with per-word confidence.
- Speaker verification (optional): an on-device voice embedding enrolled from about 30 s of speech, which rejects other voices.
- Recognition biased toward the screen: the names in the current page map (titles, channels, button labels) and the personal vocabulary (§6.8) are passed to the recognizer as context words.
That way "Bohemian Rhapsody" is recognized as written when it is on screen.
Model files reach the service as read-only handles, like the inference service's.
- A possible bonus: the same recognizer could answer the Web Speech API ( ) for web pages locally.
Today that API is unavailable or Google-backed.
In MoltNet it would first need its own fingerprinting review, since a page could time the recognizer or compare its results.
The direct-command grammar first: a small parser, deterministic and unit-tested, with synonyms and number words.
It handles most commands in milliseconds.
Choosing: when the utterance is a choice, the matcher (§6.4) resolves it against the current page map.
Everything else goes to the planner: the existing on-device model with constrained JSON output, given the page map and the conversation so far.
It returns one action or a short plan, which is spoken and shown before it runs.
Context: the last list the browser read, the last item chosen, and the current field.
This lets "the next one", "play it again" and "read it back" work.
6.3 Page map - Source: gives the page's accessibility tree: roles, names, states, values, headings, landmarks, links and media, across frames and shadow DOM.
This is the same structure screen readers use.
- Items: the map numbers what can be acted on and detects repeated structures (lists of results, cards, rows) to read as one list with their distinguishing fields.
- The browser UI too: the views have accessibility trees, so the browser's own bubbles, prompts, menus and settings get numbers and names.
- Fallback: where the accessibility tree is poor (canvas apps, unlabeled controls), the vision model describes the screenshot (masked as today), and the existing element snapshot fills gaps.
- Shared with the agent: this replaces its 40-element snapshot with a richer, more robust one.
6.4 Matching what was said to what is on screen - Ordinals and numbers first: "fourth", "number four", "4", "the last".
- The planner as last resort: for descriptions ("the live one", "the shortest", "the one from 1985"), the on-device model ranks the candidates.
- Thresholds: below a confidence threshold, or when two items are close, the browser asks.
- Tests: every scorer is a pure function with tests built from real result lists and real recognition errors.
6.5 Actions - On pages: accessibility actions (default action/click, focus, set value, scroll into view, increment and decrement).
Blink treats these as user interaction, as for OS assistive technology, so media starts with sound, full screen works, and pages see a trusted click.
- Text entry: set-value or the input method path, with the page's input events.
- Browser commands: Chromium's command IDs (back, reload, new tab, zoom, find) and the media session for playback control.
- Safety: every action still passes (http(s) only, credential fields, untrusted-text fencing) and §7's confirmations.
6.6 Speaking and showing - Voices: - Phase 1 uses with the platform's voices (Windows SAPI/OneCore, macOS, speech-dispatcher on Linux).
- Phase 2 adds a bundled neural voice in the speech service, registered through , so it sounds the same on every OS.
- In MoltNet the voice list pages see through is then the same everywhere, which closes a fingerprinting surface.
- The overlay: a MoltBrowser view above the page holds the caption bar, the numbers and the focus ring.
It is drawn by the browser, so pages can't read or fake it.
- WebMCP: where a site offers WebMCP tools, they are used as the agent already does.
- When a site changes: skills are data, versioned and tested against stored copies of the pages.
A broken skill falls back to the generic page map.
6.8 Learning from use The navigator gets better for each user from what they say and what worked, all on the device: - Routines taught by voice.
After a task succeeds, "remember this as my news " saves it as a workflow in the automation engine's format, under its trust policy.
The agent can already save a run as a draft workflow; voice mode adds naming and starting it by voice.
For a new request, the planner is shown the most similar saved routines for the site as worked examples.
This follows the published Agent Workflow Memory method, which reports large gains on web-task benchmarks.
Names the user says often (artists, contacts, sites) and their corrections ("no, I said ...") are kept as a personal vocabulary.
The recognizer is biased toward them, and toward the names on the current page (§6.1).
When the generic page map works on a site, the parts it used (search box, result list, player) are remembered for that site.
A hint that fails is dropped.
- The user's own voice (Phase 4): adaptation to impaired or atypical speech from samples the user chooses to record.
Everything learned is listed in settings, can be deleted by voice, and stays on the device.
Nothing is learned in MoltNet windows.
Trust and safety for voice Voice is a new way into the browser, so it gets the same care as clicks.
- Other people and devices: someone else in the room, a TV, a voice assistant.
- Replay: a recording of the user's own voice.
- Text injection: a page's text that tries to steer the planner ("ignore the user and ...").
The agent's untrusted-text fencing already handles this.
- Misrecognition that leads to a wrong irreversible action.
- Reading out the wrong thing: speaking private information aloud in front of others.
7.2 Defenses - Echo cancellation against everything the browser plays removes most page audio from the microphone.
While a page plays audio, commands also need a slightly higher confidence.
- Speaker verification (optional) accepts only the enrolled voice.
- Page content never becomes a command.
Text from pages goes to the planner only inside the untrusted fence, as today.
- Confirmations: buying, sending, posting, deleting, changing account or security settings, sharing location or files, and anything the agent's probe already asks about are read back first.
They need a spoken "yes" heard by the speech service.
They are typed only from the vault ( ), never by dictation; the user says "use my saved password".
- Rate limits: sensitive actions are capped per minute, and a run of failed confirmations stops the voice session.
7.3 A voice gesture in place of a real click Today several decisions count only with a physical click: the page's transient user activation, consumed by .
In voice mode, the browser gives them a voice gesture instead.
It is a one-time capability the speech service mints when it hears the user confirm a specific prompt, which the browser has spoken and shown.
It works like this: - The prompt shows a random confirmation word (for example "say harbor to allow").
A recording or a page's audio can't predict it.
- The capability is bound to that prompt and expires in seconds.
- Pages can't mint it: it comes from the speech service, not from a renderer.
The design and threat model get their own security review before they ship (Phase 3).
7.4 MoltNet - On-device: voice mode works in MoltNet windows, and all speech stays local.
- Pages don't hear the user: they never receive the user's voice through voice mode.
They only see the text the browser types and the clicks it makes, as with a keyboard.
- Not detectable: pages can't tell voice mode is on.
The overlay isn't part of the page, and accessibility actions look like ordinary clicks.
Privacy - Audio: processed in memory and dropped.
- Transcripts: a history of commands is off by default.
If the user turns it on, it is kept locally like AI memory and can be deleted by voice.
- No new network traffic: model files are downloaded like the others (pinned hashes), and nothing else.
